# Chat Domain Contract

Status: Accepted and implemented
Date: 2026-11-06

## Purpose

This document defines the core business rules for accepting a user message
and scheduling an AI agent run.

These rules are independent of HTTP, databases, message brokers, Redis, and
AI providers.

## Domain language

### Tenant

A tenant is the primary security and ownership boundary.

Every conversation, message, agent run, event, cache key, and persistence
operation must be associated with exactly one tenant.

### Actor

An actor is an authenticated user or service identity.

The application derives the actor and tenant from trusted authentication
context. They must not be trusted solely because they appear in a request
body.

### Conversation

A conversation owns ordering and lifecycle information for chat messages.

A conversation does not contain an in-memory collection of all messages,
because enterprise conversations can grow without a practical bound.

### Message

A message is an immutable chat record.

Messages are append-only. Editing or regenerating content creates another
record or revision instead of modifying the original message.

### Agent run

An agent run represents one asynchronous attempt to produce an assistant
response from a user message.

Provider-specific request and response objects are not part of the domain.

## Tenant invariants

- Every tenant-owned entity has a non-null `tenant_id`.
- An entity's `tenant_id` never changes.
- Linked entities must belong to the same tenant.
- Cross-tenant references are always invalid.
- Tenant identity comes from trusted authentication context.
- Tenant isolation is enforced by authenticated actor context, application
  checks, tenant-scoped queries, and composite database constraints.
- PostgreSQL row-level security remains optional defense-in-depth work for a
  hostile shared-database deployment.

## Identifier invariants

- Entity identifiers are opaque and strongly typed by domain concept.
- New identifiers are generated by the server.
- The nil UUID is invalid.
- A tenant ID cannot be substituted for a user, conversation, message, or run
  ID even though each identifier is UUID-backed.

## Conversation invariants

- A conversation is either `active` or `archived`.
- An archived conversation cannot accept new messages.
- A conversation version is non-negative.
- Every accepted mutation increments the conversation version.
- Message ordering uses a conversation-local sequence number, not timestamps.
- A message sequence number is positive and never reused.

## Message invariants

- Messages are immutable after creation.
- Message content cannot be blank.
- Message content has an explicit maximum length.
- A user message has an authenticated actor.
- A user message has an idempotency key.
- Timestamps are timezone-aware and normalized to UTC.
- Server-assigned sequence numbers determine ordering.

## Idempotency invariants

Idempotency keys are:

- non-empty;
- bounded in length;
- opaque;
- case-sensitive;
- never silently trimmed or rewritten.

Replay detection belongs to the application and persistence layers.

The eventual uniqueness scope is:

`(tenant_id, conversation_id, operation, idempotency_key)`

Reusing a key with the same request payload returns the original result.
Reusing the key with a different payload produces a conflict.

## Accept-user-turn operation

The first domain operation accepts one user turn.

It receives:

- a conversation;
- a trusted tenant identifier;
- an authenticated actor identifier;
- user message content;
- an idempotency key;
- caller-generated identifiers;
- a caller-supplied timezone-aware timestamp.

It verifies:

- the trusted tenant owns the conversation;
- the conversation is active;
- the content is valid;
- the timestamp is valid.

It produces:

- an updated conversation;
- one immutable user message;
- one queued agent run linked to that message.

The operation performs no network, filesystem, database, Redis, or
AI-provider I/O.

The persistence implementation commits the updated conversation, user
message, queued agent run, idempotency receipt, and outbox event in one
database transaction.

## Agent-run lifecycle

The initial state is `queued`.

Allowed transitions are:

```text
queued  -> running
queued  -> failed
queued  -> cancelled

running -> succeeded
running -> failed
running -> cancelled
```

`succeeded`, `failed`, and `cancelled` are terminal states. A terminal run
cannot transition again.

A retry creates a new run; it does not reopen a terminal run.

A cancellation request does not claim that running work has stopped. A
running run becomes `cancelled` only after the worker confirms cancellation.

## Time rules

- Domain timestamps must be timezone-aware.
- Aware timestamps are normalized to UTC.
- Domain operations receive time from their caller.
- Domain entities do not call the system clock internally.
- Tests use fixed timestamps and never sleep.

## Concurrency boundary

An in-memory conversation version does not prevent database races.

Persistence enforces optimistic concurrency with a compare-and-swap operation
equivalent to:

```sql
UPDATE conversations
SET version = :new_version
WHERE tenant_id = :tenant_id
  AND id = :conversation_id
  AND version = :expected_version;
```

Updating zero rows represents a concurrency conflict.

## Concerns outside this domain contract

The application and infrastructure layers now implement HTTP, SQLAlchemy,
transactional outbox processing, provider adapters, retry, Redis, and
WebSockets. They remain outside the domain model because business entities
must not depend on those technologies.

The following product concerns remain intentionally deferred:

- PostgreSQL row-level security;
- token streaming;
- RAG, embeddings, and document ingestion;
- tool execution;
- organization-specific moderation and retention;
- billing and usage accounting.
